## Требования (согласовано)

| Тема | Решение |
|---|---|
| Кто создаёт очереди | Назначенный ответственный потока вручную **или** бот автоматически по расписанию |
| Порядок в очереди | Запись открывается по таймеру, дальше — кто первый нажал |
| Открытие записи | За N часов до пары (N задаётся для каждой пары в расписании) |
| Межгрупповые очереди | Постоянные «потоки» (stream) — набор чатов; очередь создаётся на поток и показывается во всех его чатах |
| Расписание | Ручной ввод ответственным в личке бота (предмет, день, время, чётность недели, N) |
| Обмен местами | Запрос → подтверждение второй стороной в личке |
| Уведомления | В личку тем, чьё место сдвинулось (при выходе — всем ниже; при обмене — двоим) |
| Без лички | Записаться можно без /start, но уведомления и обмен такому студенту недоступны (бот предложит открыть личку) |
| Запись за другого | Любой может записать **одного** одногруппника: выбор из списка известных боту участников потока, а если человека нет в списке — по имени текстом. Запись одногруппника принадлежит ему (видит в «Моих очередях», получает уведомления, сам выходит/меняется); записавший тоже может её убрать. Запись «по имени» принадлежит записавшему |
| После пары | Просто список: сдача не отслеживается, очередь закрывается сразу после окончания пары (closes_at = конец пары) |
| Хранение | Закрытые очереди удаляются через 7 дней. Внешняя копия — только настройка (потоки, ответственные, расписание) в JSON, раз в семестр + `/backup` вручную, восстановление `/restore` |
| Модерация | В MVP ответственный **не** удаляет/не переставляет людей. Архитектура оставляет место (см. «Точки расширения») |
| Стек | Python 3.13, aiogram 3, SQLite (aiosqlite), APScheduler |

```
├── .env                  # BOT_TOKEN=... (НЕ коммитить)
├── db/
│   ├── schema.sql        # таблицы
│   ├── database.py       # соединения, транзакции, write lock
│   └── repo.py           # запросы к БД
├── handlers/
│   ├── group.py          # кнопки в групповых чатах
│   ├── private.py        # личка: мои очереди, обмен, запись одногруппника
│   ├── admin.py          # ответственный: потоки, расписание, ручное создание
│   └── swap.py           # обмен местами: выбор, запрос, подтверждение
├── services/
│   ├── queue_service.py  # запись / выход / обмен (транзакции + lock на очередь)
│   ├── permissions.py    # кто что может (точка расширения для модерации)
│   ├── notifier.py       # уведомления о сдвиге мест
│   ├── renderer.py       # текст + клавиатура сообщения очереди, синхронное обновление во всех чатах
│   └── scheduler.py      # автосоздание, открытие и закрытие очередей
├── keyboards.py
└── tests/                # pytest
```

## Модель данных

- `users` — tg_id, имя, username, `can_dm` (нажал ли /start)
- `chats` — групповые чаты, куда добавлен бот
- `streams`, `stream_chats` — поток и его чаты
- `stream_admins` — ответственные потока
- `stream_members` — участники потока, известные боту (Telegram не даёт список участников группы; запоминаем всех, кто нажимал кнопки / писал команды в группах потока)
- `schedule` — stream_id, предмет, день недели, время начала, длительность (по умолчанию 90 мин), чётность (все/чёт/нечёт), open_before_hours
- `queues` — stream_id, предмет, дата/время пары, opens_at, closes_at, статус (`scheduled`/`open`/`closed`)
- `queue_entries` — queue_id, position, user_id (владелец записи), guest_name (человек вписан текстом, владелец — записавший), added_by (кто создал запись)
- `queue_messages` — queue_id, chat_id, message_id (для синхронного редактирования)
- `queue_events` — журнал всех изменений очереди (actor_id, тип, payload, время)
- `swap_requests` — queue_id, from_entry, to_entry, статус, created_at (истекает, если место сдвинулось)

## Ключевые правила

- Один пользователь — одна своя запись + может записать максимум одного другого человека в одну очередь (`MAX_ADDED_OTHERS`).
- Владелец записи (`user_id`) получает уведомления и участвует в обмене; убрать запись может владелец или тот, кто её создал (`added_by`).
- Все изменения очереди — транзакция под общим write lock (`Database.transaction()`): записи идут строго по одной, нет гонок при одновременных нажатиях (проверено тестом на 20 одновременных записей).
- Состояние только в БД → после перезапуска ничего не теряется; задачи планировщика восстанавливаются из БД при старте.
- Обмен невозможен, если у второй стороны нет лички; запрос отменяется при любом изменении позиций участников.
- Редактирование сообщений в группах — с троттлингом (лимиты Telegram на edit).

## Точки расширения (модерация ответственным — после MVP)

Чтобы потом добавить удаление/перестановку без переделок, в MVP сразу закладываем:

- **Все изменения очереди — только через `queue_service`** (`join`, `leave`, `swap`, а позже `remove`, `move`). Хендлеры никогда не меняют `queue_entries` напрямую. Каждая операция принимает `actor_id` — кто инициировал действие.
- **Единая функция сдвига позиций** в `queue_service` (`_reposition`) — её используют и выход, и обмен, и будущие `remove`/`move`.
- **Уведомления строятся по разнице позиций «до/после»** (`notifier.notify_diff(before, after, reason)`), а не по типу операции. Любая новая операция автоматически уведомит тех, чьё место сдвинулось.
- **Проверка прав в одном месте** — `permissions.can(user, action, queue)`; в MVP `remove`/`move` всегда `False`, позже — `True` для `stream_admins`.
- **Журнал `queue_events`** (queue_id, actor_id, тип, payload, время) — пишем с первого дня: пригодится для споров «кто кого выкинул» и для отката.
